~22k lines of my own Python across 28 experiment labs, 55 scripts, and a gate suite, plus the cluster tooling that runs them.

KernelAscent makes recursive self-improvement falsifiable in code. One observation drives the engineering: "the model got better" is confoundable with "the model sampled more." Every rung is therefore a differenced design that isolates one causal channel. The weight-RSI lab runs three arms at matched compute. A lineage learner LoRA-trains on its own verified kernels and carries weights forward. A reset learner re-initialises each round and trains on that round's data alone. A best-of-N arm samples the frozen base at the cumulative budget k*(r+1). Both learners see identical per-round data, so lineage − reset isolates weight accumulation. Best-of-N holds samples equal, so lineage − best-of-N separates training from search. The self-play lab lifts the same logic one level. Its three arms — STATIC, FROZEN-AUTHOR, LIVE-AUTHOR — differ only in who writes the tasks, which makes L−F the self-referential term. An anti-reward-hacking gate rejects constant-output, identity, no-op and trivial-runtime proposals before they reach the frontier and logs each as model-proposed or programmatic backstop. The grader builds an fp32 gold model and derives each task's tolerance from the reference's own dtype error (bound = max(2e-2, 2·ref_err)). Speed normalises against a per-task roofline ceiling, so the score measures captured physical headroom. Candidates execute in a subprocess, so a malformed kernel cannot poison the trainer's CUDA context.

I am most proud of what the instrument work uncovered. Two findings came from interrogating the measurement, not the models. The first is the metric. The headroom score takes best-of-k, and best-of-k is identical for a model that solves a task 1-in-k and one that solves it k-in-k. On this bank it pins at 0.50 once a single candidate reaches parity. A model improving from 1-in-10 to 9-in-10 moves the score by zero, and that reliability gain is the channel self-training acts through. I re-scored the same runs under pass-rate (n_ok/k per task) and registered it as post-hoc in a pre-registration amendment with its falsifier fixed first. The flat null became monotone compounding. It beat the reset learner, beat matched-budget search by +0.94, and transferred to a held-out task family. One design, one seed, one variable changed, opposite conclusions. The second is the state machine. These runs chunk across cluster walltimes, so cross-round state is the hypothesis. My resume restored history and the round counter but not the LoRA adapter. Every resumed chunk restarted all three arms from base weights while the round numbering continued. Nothing errored and the queue looked healthy. trainC collapsed at the round named by resumed_at in all 18 resumed cells. The repo now treats defence as first-class: 34 audit gates over cross-referenced claims, a meta-gate that fails the suite when a gate lacks a negative test, provenance stamped into every artifact including whether Triton could build, atomic tmp-then-rename writes, resume paths that exit 3 and refuse over continuing on base weights, and a ledger that separates a cell that advances from one that repeats.

Four parts of the code I would build differently. Configuration is the worst of them. KA_SCORE, KA_EXTRACT and KA_MAX_NEW are read from os.environ at import time in separate modules. Two arms of one comparison generated at 2048 and 900 tokens because of it, and two rungs of the ladder still run at 2048 and 1200. I would construct one frozen config object at entry, validate it, stamp it into the artifact, and diff it across runs. Incomparability becomes a type error. Second, each lab hand-rolls its own resume, and three of four got it wrong in different ways. One dropped the adapter, one wrote non-atomically, one logged a failed restore and continued on base weights. I would have each lab declare its cross-round state once and let shared machinery own the write, the restore and the refusal. Third, the metric lives as a branch inside eval_tasks keyed on a string. That couples scoring to generation and blocks re-scoring a finished run. I would persist per-candidate verdicts and compute every metric from the artifact, which turns the best-of-k blindness into an afternoon's analysis. Fourth, the grader returns positional tuples that callers unpack by position; named records would make a mismatched field fail at the call site. I would add one property test above all others: a resumed run must produce bit-identical output to an uninterrupted one.
