Code sample, KernelAscent

Repository https://github.com/ahmd-mohsin/KernelAscent

The most relevant files are kernelascent/v3/lab_compounding.py (weight-RSI, three-arm), kernelascent/v3/lab_selfplay_rsi.py (self-play, three-arm), kernelascent/agent_bench.py (grader, roofline, scoring), scripts/consistency_audit.py with tests/test_audit_gates.py (claim gates and their negative tests), and BENCHMARK_LOG.md (the full experimental record). The work is roughly 22k lines of my own Python across 28 experiment labs, 55 scripts, and a gate suite, plus the cluster tooling that runs them.

Notation. θ(t) is the LoRA adapter weights after round t, where LoRA is a low-rank update trained on top of a frozen base model. θ(0) is the untrained base. π(θ) is the sampling distribution those weights induce over kernel source code. D(t) is the set of kernels the model generated and the grader verified in round t. T is the training map that takes weights and data to new weights. C(t) is held-out capability, the mean score on tasks never trained on. k is the number of candidates sampled per task, r is the round index, and p is the probability that one sampled candidate verifies. Triton is the GPU kernel language the models are asked to write in.

KernelAscent makes recursive self-improvement falsifiable in code, and the code is organised around the recurrence that defines it. A learner maps weights and self-generated data to new weights, θ(t+1) = T(θ(t), D(t)), and the data is drawn from the model's own policy π(θ(t)). Compounding is a claim about the derivative of that map. It says this round's gain grows with the capability already reached, ∂C(t+1)/∂C(t) > 0, and it is confoundable with a model that simply samples more. My three-arm design is a finite-difference decomposition of T built to break that confound. The lineage arm computes T(θ(t), D(t)) and keeps the full recursion. The reset arm computes T(θ(0), D(t)) on byte-identical data, which removes the weight channel and holds data quality fixed. The best-of-N arm never trains and samples θ(0) at the cumulative budget k(r+1), so by round r it has drawn exactly as many candidates as the lineage arm. Lineage minus reset isolates accumulation. Lineage minus best-of-N isolates training from search at equal samples. The self-play lab measures an interaction rather than a main effect, because solver weights and task distribution both move. Its arm S holds the task frontier fixed, arm F escalates the frontier with tasks written by the frozen base, and arm L escalates it with tasks written by the evolving model. L minus S gives the total curriculum effect, F minus S gives the effect with no author update, and L minus F gives the cross term between author quality and solver quality. That cross term is the self-referential signal. Scoring maps heterogeneous tasks onto one scale through a per-task affine transform anchored on physics, score = 0.5 + 0.5·clamp((s−1)/(c−1)). Here s is the candidate's speedup over a torch.compile baseline and c is the roofline ceiling, c = t_compiled/t_roofline, with t_roofline = max(FLOPs/peak, bytes/bandwidth), the time an ideal kernel would need given the hardware's arithmetic and memory limits. The score reports the fraction of physically achievable headroom captured, so a task with 1.1x of available slack and a task with 40x weigh the same in the mean, and 0.5 means correct at parity with the baseline.

I am most proud of what the instrument work uncovered, because both findings came from interrogating the measurement instead of the models. The first is a statement about an estimator. The headroom score takes a maximum over the k candidates sampled for a task, so the observable tracks 1 − (1−p)^k, the chance that at least one of k draws verifies. Its derivative with respect to p collapses as p grows. At k = 10 a model moving from p = 0.1 to p = 0.9 changes that quantity by almost nothing, and on this bank the score pins at 0.50 the moment one candidate reaches parity. Self-training acts on p. My estimator was blind to the one parameter the hypothesis predicts. I re-scored the identical runs under pass-rate, p̂ = n_ok/k, where n_ok counts how many of the k candidates verified. That estimator is unbiased for p and keeps its sensitivity across the whole range. I registered the change as post-hoc in a pre-registration amendment with its falsifier fixed first. The flat null became a large effect. Lineage rose to within a few points of the pass-rate ceiling, beat the reset learner by about half a score point, beat matched-budget search, and transferred to a held-out task family. One design, one seed, one variable changed, opposite conclusions. The second finding is about state. These runs execute in chunks bounded by cluster walltime, so θ(t) crossing a chunk boundary is the recurrence itself. My resume restored the round history and the round counter but not the adapter, so every resumed chunk silently recomputed T(θ(0), D(t)) while the round index kept climbing. Nothing errored and the queue looked healthy. The giveaway was trainC, the model's score on its own training split, collapsing at exactly the round recorded in resumed_at, the field naming where a run picked up. It did so in all 18 resumed cells. The repo now treats defence as first-class. It runs 34 audit gates over cross-referenced claims and a meta-gate that fails the suite when a gate lacks a negative test, a test that plants the error and asserts the gate fires. It stamps provenance into every artifact, including whether Triton could compile at all on that node. It writes every artifact to a temporary path and renames it into place, so a job killed mid-write leaves the old file intact. A resume that finds no adapter checkpoint exits with status 3 and refuses rather than continuing on base weights. A ledger fingerprints each run so a cell that advances is distinguishable from one that repeats.

Five parts of the code I would build differently. The first is the evaluation set, and I found it by testing a fix that failed. Pass-rate removed the best-of-k blindness but kept a bound of its own, since n_ok/k cannot exceed 1 and the lineage arm reaches 0.96 by round four. I proposed scoring verified solutions per unit compute instead and computed it from the stored rounds. The cumulative form rose where pass-rate was flat, which is an artifact, because a cumulative sum climbs whether or not anything compounds and so cannot falsify the hypothesis. The marginal form plateaued. My held set is 5 tasks at k = 10, so a round yields at most 50 verified candidates and every per-round score on a fixed set inherits that bound. The ceiling sits in the denominator and no numerator fixes it. Unbounded compounding needs a task supply that stays ahead of the learner, which is what the self-play rung exists to provide and what it failed to deliver at 2 accepted proposals from 68. I had treated the saturating metric and the silent author as two limitations. They are one. I would build the difficulty generator first, driving the DSL mutation space with the validity and learnability gates applied to a moving frontier rather than a fixed held set. The second thing I would change is the optimisation itself. My loop maximises verified reward on self-generated data with nothing holding θ(t) near θ(0), so the step size each round is whatever the data happens to produce. I would make it a regularized RSI objective, θ(t+1) = argmax E[R] − λ·KL(π(θ) ‖ π(θ(0))). Here R is the verified score of a sampled kernel, KL is the Kullback-Leibler divergence measuring how far the updated policy has moved from the base policy, and λ sets how strongly that movement is penalised. My mechanism probe already logs LoRA drift, the norm of the weight change split by transformer depth, and retention, the fraction of round-0 solved tasks still solved. It finds that sustained drift and retention discriminate the models that compound. A trust-region term acts on exactly those two quantities, so sweeping λ converts drift magnitude and forgetting from observed outcomes into a dial I set, and it gives the recurrence a contraction parameter instead of an empirical one. Third, configuration. The environment variables KA_SCORE, KA_EXTRACT and KA_MAX_NEW select the scoring metric, the code-extraction policy, and the generation token budget. All three are read from os.environ at module import time in separate files. Two arms of one comparison generated at 2048 and 900 tokens because of it, and two rungs of the ladder still run at 2048 and 1200. I would construct one frozen config object at entry, validate it, stamp it into the artifact, and diff it across runs, which makes incomparability a type error. Fourth, each lab hand-rolls its own resume and three of four got it wrong in different ways. One dropped the adapter, one wrote non-atomically, one logged a failed restore and continued on base weights. I would have each lab declare its cross-round state once and let shared machinery own the write, the restore and the refusal. Fifth, the scoring metric lives as a branch inside eval_tasks, the function that samples and grades a task set, and it is selected by a string read at run time. That couples scoring to generation and blocks re-scoring a finished run. I would persist the per-candidate verdicts and compute every metric from the stored artifact, which turns the best-of-k blindness into an afternoon of analysis rather than a month of compute.
