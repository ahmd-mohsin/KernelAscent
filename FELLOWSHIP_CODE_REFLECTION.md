---

KernelAscent is an attempt to make recursive self-improvement **falsifiable in code** rather than asserted from a rising curve, and nearly all of the engineering follows from one observation: "the model got better" is trivially confoundable with "the model sampled more," so every rung of the ladder has to be a *differenced* design where the contrast isolates one causal channel. In the weight-RSI lab this is a three-arm loop run at matched compute: a **lineage** learner that LoRA-trains on its own verified kernels and carries weights forward, a **reset** learner re-initialised every round and trained only on that round's producer data, and a **best-of-N** arm that is the frozen base sampled at the *cumulative* budget `k*(r+1)`. Both learners see byte-identical per-round training data, so `lineage − reset` isolates weight *accumulation* — the thing "compounding" actually names — while `lineage − best-of-N` isolates training from search at equal samples, which is the comparison that stops a self-improvement claim from being a sampling artifact. The self-play lab applies the same logic one level up, where the interesting quantity is self-reference: three arms (**STATIC** fixed frontier, **FROZEN-AUTHOR** escalating frontier authored by the frozen base, **LIVE-AUTHOR** escalating frontier authored by the evolving model) decompose curriculum benefit from author co-evolution, so `L−F` — and only `L−F` — is the self-referential term, with every self-authored task passing an anti-reward-hacking gate (rejects constant-output, identity, no-op, and trivial-runtime tasks) and its provenance logged as model-proposed versus programmatic backstop. Underneath, correctness is graded against an **fp32 gold** model with a per-task tolerance derived from the reference's own dtype error (`bound = max(2e-2, 2·ref_err)`) rather than a global epsilon, speed is normalised against a **per-task roofline ceiling** (`max(1.1, min(50, t_compiled / t_roofline))`) so the score measures captured *physically available* headroom instead of a fixed anchor some tasks cannot reach and others saturate trivially, and every candidate executes in an isolated subprocess so a malformed kernel cannot poison the trainer's CUDA context mid-run.

The deeper lesson, and the part of the work I am most proud of, is that measuring recursive self-improvement turns out to be **mostly a problem of defending the measurement against yourself** — and the two findings that matter most both came from interrogating the instrument rather than the models. First, the scoring metric: the headroom score is a *best-of-k* quantity, and best-of-k is mathematically identical for a model that solves a task 1-in-k and one that solves it k-in-k. On this task bank it saturates at exactly 0.50 the moment a single candidate is correct-at-parity, so a model going from 1-in-10 to 9-in-10 — an enormous gain in *reliability*, which is precisely the channel self-training acts through — registers as **exactly zero movement**. Re-scoring the identical runs under a pass-rate metric (`n_ok/k` per task, declared post-hoc in a pre-registration amendment with its falsifier fixed in advance) turned a flat null into monotone compounding that beats the reset learner, beats matched-budget search by up to +0.94, and *transfers to a held-out task family the model never trained on* — the check that separates capability from sharpening on the held set. One design, one seed, one variable changed, opposite conclusions. Second, the state machine: because these runs are chunked across cluster walltimes, resume logic is not plumbing — **cross-round state *is* the hypothesis**. My resume restored `history` and the round counter but not the LoRA adapter, so every resumed chunk silently restarted all three arms from base weights while the round numbering continued, deleting the accumulation the lab exists to measure. Nothing errored; the queue looked healthy; the signature was `trainC` collapsing at exactly the round named by `resumed_at`, in all 18 resumed cells with no exceptions. That class of failure is why the repo now treats defensive infrastructure as first-class: a consistency audit of 34 gates over cross-referenced claims, a **meta-gate that fails the suite if any gate lacks a negative test** (five gates had silently matched nothing at some point), provenance stamped into every artifact including whether Triton could *build*, atomic tmp-then-rename writes because the walltime kill lands mid-write by construction, resume paths that **exit non-zero and refuse** rather than continue on base weights, and a progress ledger that distinguishes a cell that is *advancing* from one that is *repeating* — both of which had previously presented identically as `TIMEOUT` and burned nineteen cells in a silent loop.

What I would most like to improve is the consequence of that same discovery: I currently have **two scorers that give opposite answers and no principled basis for preferring one**, which is an honest state to be in but not a finished one. The right fix is not a third board but a single metric that is continuous in the quantity RSI actually moves — expected verified throughput per unit compute, say — so reliability and speed are commensurable by construction rather than reconciled in prose; as it stands, a pre-registration amendment forbids pooling them, which protects the claims but leaves the benchmark speaking with two voices. The statistical foundation needs the same treatment: the strongest results rest on n=2 trajectories per arm over 5 held and 4 transfer tasks, and a 124-task DSL-generated bank with leakage-resistant *family* splits already exists but the capability and compounding rungs have not been re-run on it, so the intervals are far wider than the design deserves. Architecturally, configuration is my weakest layer — semantically load-bearing settings (`KA_SCORE`, `KA_EXTRACT`, `KA_MAX_NEW`) are read from the environment at import time in several independent modules, which is how two arms of a single comparison ended up generating at 2048 and 900 tokens and how two rungs of the ladder still run at 2048 and 1200; that should be one explicit, validated config object, constructed once, stamped into the artifact, and diffable across runs, so incomparability becomes a type error instead of a discovery. Finally, the gate suite is strong precisely where it was written in response to a specific failure and thin everywhere else: five test files against ~22k lines, with the labs' own round loops covered only end-to-end on the cluster. The property I would most like to test directly — that a resumed run is *bit-identical* to an uninterrupted one — is exactly the invariant whose violation cost me the most, and it is still checked by inspection rather than by a test.
