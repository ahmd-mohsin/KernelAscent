Does self-improvement actually compound?

KernelAscent measures agents that improve with experience. It asks the sharp question — not "can an agent improve?", but: when an agent improves the research procedure it uses, does using that improvement help it produce a better next improvement, and does it repeat? We separate the actor that produces an improvement from the target it edits, so a later producer earns credit only if it beats an earlier one on the same target.

The mechanism

An agent's state U is its executed research procedure — how it proposes candidates, evaluates them, and selects. develop runs the procedure on a fresh task under a fixed budget and returns a quality Q. revise lets an actor edit a copy of a target procedure to produce a child. In a causal fork, two different actors edit the identical target — so a later actor is credited only if it produces a genuinely better child. That is what turns "the score went up" into a testable causal claim; a rising task score, or merely editable source code, is not enough.

Findings

We tested this on four substrates — a GPU-kernel flagship, a verifier-improvement loop, a GPU inference world, and an efficiency-of-experimentation lab engineered to give recursion its best chance — plus live-model runs, with matched-budget controls, replication on held-out instances, and transfer. Every effect is an estimate with a 95% CI, judged against a prespecified meaningful effect δ = 0.05.

Agents improve their research procedure with experience — first-order, causal, capability-graded, and transferable — but this does not yet produce a resolved causal producer advantage or recursive compounding.

What is resolved (positive)

  • First-order improvement is real, causal, and capability-graded. Two capable models improve their procedure (opus-5 q₁−q₀ = +0.30 > gpt-oss +0.10 > deepseek +0.02); the child beats the unchanged target (N₁ resolved for two models); and it beats a frozen-procedure-with-growing-memory control — so it is the procedure change, not accumulated data.
  • Learned procedures transfer. A procedure evolved on one task family, deployed on a structurally different family, beats the baseline there by +0.091 [0.037, 0.146].
  • Procedure quality is a real lever. The good procedure beats brute-force search by +0.15 → +0.18 as budget tightens.

What is a bounded negative

  • No resolved causal producer advantage: F₁ = +0.019 [−0.013, 0.051] at n = 40, bounded below δ.
  • No compounding: F₂ ≈ 0 on every substrate, including one engineered to favor it.
  • Iterating ≠ constructing: iterative self-improvement underperforms building the good procedure directly (−0.18) and matches direct search at equal total budget.

Dataset & splits

The curated code-task bank is difficulty-graded and executable-validated — a single strong curator, diversity-forced across problem families, then re-validated and deduplicated. It ships with a public / held-out split so the leaderboard cannot be overfit.

  • Public split: 75 tasks (easy 21 · medium 17 · hard 18 · ultra 19), 14–16 distinct problem families per tier — on HuggingFace and in dataset/tasks/public/.
  • Held-out test: 34 tasks (~35%), split deterministically by name hash, never published — the private leaderboard set.
  • Kernel track: a separate procedural GPU-kernel bank (1000+ tasks, 6 families) powers the capability leaderboard.

Reproduce & submit

Everything is dockerized behind a single scoring command; the leaderboard is scored on a private held-out split.

docker build -t ka -f docker/Dockerfile .
docker run --rm -e AWS_SHARED_CREDENTIALS_FILE=/creds -e AWS_PROFILE=bedrock \
  -v $PWD/creds:/creds:ro -v $PWD/out:/out ka \
  --track capability --api-model us.anthropic.claude-opus-5 --tier medium
# writes out/scorecard.json

Then open a model-submission issue with your scorecard. See docker/README.md.
