Compounding kernel optimization

KernelAscent

KernelAscent asks whether models get better at writing GPU kernels. A model writes a kernel. We grade it for correctness against an fp32 reference and for speed against a baseline. Task 1, Capability measures raw skill in one shot. Task 2, Weight RSI measures recursive self improvement through weight training, for open weight models. Task 3, Procedure RSI lets open and closed models improve their own executable research procedure, weights fixed. Open and closed models both compete on Tasks 1 and 3. Task 2 needs weight access.

00 / Key findings

What we found

Self-training sharpens what a model already covers; it does not explore. In GPU-kernel optimization, compounding is coverage-limited — and coverage is not self-generated.

How these numbers are counted. The independent replicate is a trajectory — one seed, one base checkpoint, one held split, one accumulated adapter — not a round. Rounds inside a run are serially dependent, so pooling them as independent overstates the evidence (it is what an earlier version of this page did). Every interval below is computed at the trajectory level, with a cluster-robust check; the naive round-level figure is shown only where it makes the correction auditable.
  • No compounding — a bounded null. Lineage vs. matched reset over multi-round rejection-sampling SFT: pooled lineage−reset = -0.010 [-0.035, +0.016] over 57 independent trajectories (228 round-comparisons), TOST-equivalent at δ=0.05, Bayes factor BF₀₁ = 5.6 — moderate evidence for the null. Robust to dropping short runs (≥3 rounds: 5.9; ≥6 rounds: 4.9). The naive round-level pooling would report BF₀₁ = 14.7; that figure is an artifact of the clustering and we do not claim it.
  • Search beats training (significant). At matched cumulative generation budget, best-of-N search beats lineage self-training: lineage−bestofN = -0.111 [-0.138, -0.083] over 57 trajectories — CI excludes zero — and search wins 84% of runs. Unlike the null, this positive strengthens under the clustering correction, because the contrast is made within a round.
  • Coverage-vs-scale (0.5B→14B). Coverage 14%→86%; below the wall pass@K ≫ pass@1 (12–17×) — the sub-2B "correctness wall" is a low per-sample success probability, not absent capability. The sharpenable band (0<p<0.2, the only mass rejection-sampling SFT can act on) is 14/28/59/79/0% at 0.5/1.5/3/7/14B: thin below the wall, absent above it.
  • 0-score forensics (8 families). The sub-3B wall is a kernel-formation failure (no_extract 57–96%), not correctness; failure marches downstream with scale: incoherence → truncation → API-hallucination → wrong-output → correct.
  • Weight-level mechanism (WHY-RSI, n=133). Reported as associations, not causal gates. Wall-crossing is 54% below 2B vs 92% at ≥2B — less frequent, not "never". RSI is an inverted-U in scale: it peaks at 2–8B (50%) and falls to 23% at ≥8B despite the largest LoRA drift (0.60) — motion without progress near the roofline. Among wall-crossers the discriminators are drift and retention; compounders show lower generation diversity (0.41 vs 0.52), so "diversity collapse causes the null" is not supported on this bank.
  • Task-3 procedure self-modify — gains are real, the "one-shot" reading is retracted. The harness asks for “≤12” strategy strings and shows 12 back. Frontier models comply exactly: 5 of 5 interpretable runs sit at 11–12 strategies from round 0 and 4 of 5 never grow at all (Astra, Sonnet 5 and Mistral Large 3 are literally 12,12,12,12,12,12). A procedure pinned at its limit in round 0 cannot be observed to keep improving, so “the model stopped” and “the harness stopped it” are not separable. Re-running the same harness with an open model at caps {12, 48, unbounded}: procedures grow when permitted (5/6 runs, reaching 18 strategies) and mean ΔQ rises monotonically −0.018 → −0.003 → +0.482, with none of the unbounded gain at round 0. Two seeds per cell, and open-vs-closed is confounded with model family, so these corroborate rather than replicate — but the closed-model pinning is visible in the already-published records and needs no new run. The apparent DeepSeek-V3.2 “self-degrade” remains a single-round artifact.
  • Task-5 self-play — undefined, not null. L−F needs the live author to produce accepted valid tasks; requiring ≥5, only 6/24 open and 5/11 closed runs qualify, and 10/11 closed rows are exactly 0.0. The dedicated diagnosis run authored zero tasks in all 8 rounds. The supported finding is narrower: free-form task proposal collapses.
  • Probe-as-intervention (secondary). Clustered on base checkpoint, probe-guided reranking beats uniform random selection at matched generation budget (+0.124 [+0.029, +0.218], 12 checkpoints), recovering 36% of the oracle headroom. But random is the weakest comparator, denominators are 5–12 tasks per run, and the within-task ranking AUC — the only estimand that explains a selection gain — was never logged, so it is unmeasured.
00b / Instrument validity

Can this benchmark detect a positive?

A benchmark that reports a null owes a second result: evidence the measurement could have reported a positive. When the headline is a difference between two arms of one pipeline, any defect that suppresses both arms equally leaves the contrast at zero while every surface check — jobs complete, kernels compile, scores populate — looks healthy. A broken instrument does not announce itself; it reports Δ ≈ 0.

Seven defects, each of which independently produced a plausible null. We publish these because the null is our headline, and a reader cannot audit a null without them.
DefectPresented asCaught by
Grader mis-imported under a wrong root“self-training does not compound”identity-kernel assertion
Grading device index absent on a 1–2 GPU allocation“the model writes bad kernels”same assertion, run on the allocation shape the jobs use
Raw generations graded without extracting the submission“the 14B teacher solves 0/29”non-zero coverage precondition

Compiled-baseline cache hitting a filesystem inode quota“4 of 6 rounds produced nothing”output-path / quota correlation

The sixth is the instructive one

We diagnosed a spike of scores at exactly 0.50 as a hardware effect: torch.compile is stronger on H100, so the headroom closed. It was plausible, it fit every number we had, and it was wrong — the default scorer never uses the compiled baseline at all. The real cause was upstream of the metric, in our own prompt:

  • The generation prompt says “a plain-torch kernel that is correct beats a fancy one that errors” — written to suppress parse failures, which it did.
  • Models complied: 0 of 86 verified kernels from the 14B model contained Triton, CUDA or load_inline — all pure-PyTorch rewrites of the reference. An independent re-harvest under the same prompt replicated it exactly: 0 of 118, for 0 of 204 across both.
  • A semantically equivalent rewrite runs at reference speed by construction: median 1.00×, 93% below 1.05×.
  • And score(correct, 1.00) = 0.50 exactly — the value 76% of all H100 scores took.
  • Both arms pinned at 0.50 ⇒ lineage − reset ≡ 0, by construction.

So the metric was never broken. It reported, accurately, that the models were not attempting the task the benchmark exists to measure — and we misread a correct measurement as a dead instrument. This inverts the lesson of the first five: there, a clean zero was a bug; here a clean zero was a finding and the bug was in the interpretation. The rule we now hold is stricter: trace the causal chain from prompt to number before naming a cause, and prefer the explanation an intervention can kill over the one that merely fits.

What is running now. A prompt A/B — identical tasks, grader, model and seed, only the prompt text differs — at 14B, plus a 32B cell to test whether scale adds anything once the model is actually asked to optimize. The three outcomes and their thresholds were fixed in code before the runs launched. If the plateau proves substantially prompt-induced, every speed-scored board here has to be re-run before it means anything, and we will say so on this page.

The seventh: the benchmark had never measured its own subject

Having traced the plateau to the prompt, we removed the steer and asked explicitly for a Triton kernel. The model solved 0 of 29 tasks against 25 of 29 under the published prompt — a clean, pre-registered, publishable result: the models try when asked and cannot produce a working kernel.

It is also false. Before reporting it we applied the known-good-input gate to the new input: a hand-written Triton kernel, correct by construction, plus a plain-torch control that must pass and a wrong kernel that must fail.

CaseResultReason
plain-torch identical to the referenceok=Trueok
deliberately wrong kernelok=Falsewrong/imprecise
hand-written correct Triton kernelok=FalseFileNotFoundError

Triton compiles a small C shim at first use and takes its compiler from $CC, which the cluster's module system sets to a host path absent inside our container. Plain PyTorch never compiles anything at runtime, so only Triton broke — and Triton is the subject of the benchmark. One environment variable fixed it; the same kernel now verifies at 0.99×.

The consequence is a corrected scope, not a corrected number: for this project's entire history, every submission that was not plain PyTorch failed for an environment reason.

It also revises our account of the sixth defect. We blamed the saturated score on the prompt's instruction to prefer plain torch — but that instruction reads as a rational adaptation to a broken grader. Tuned against a harness where Triton always failed, plain torch genuinely was the only thing that worked. The prompt and the grader were coupled, and the grader came first. A configuration that looks inexplicably conservative may be compensating for a defect — and because the defect never appears in any result, the workaround looks like a design choice indefinitely.

Two things made this catchable before publication. Failure reasons now propagate — the grader had always computed a reason and discarded it one line later, so every failure in project history was a bare False, and “model writes Triton, Triton grades False” reads naturally as a claim about the model. And, more transferably: when an experiment starts producing a new kind of artifact, re-instantiate the known-good gate for that kind. “The grader works” was true and useless; “the grader works on Triton” was the question, and nothing was asking it.

Reachability: the range check, made into a number

“Check the metric has range” is advice until it is a number. Reachability is the fraction of bank tasks where the frozen base already clears the scoring anchor. It falls out of the calibration pass, costs nothing extra, and is known before any experiment runs.

BankTasksAdmittedReachability
Hand-curated (29-task)29231 / 29  (3.4%)
Generated DSL (456-task)45618057 / 456  (12.5%)

Reachability of 3.4% means that on 28 of 29 tasks every success the base produced landed at parity — the score had one attainable non-zero value, and the contrast between two arms was pinned before a single round ran. We would now decline to run a speed-scored compounding study on such a bank, and we publish the statistic for any bank we ship.

What this does not say. It is measured against eager PyTorch at a fixed 1.5× anchor, which is what the default scorer uses; the roofline ceiling does not enter it. So it licenses no claim about torch.compile, and a bank of generated references may be easy to beat for reasons that do not transfer. Reachability is necessary for a usable substrate, not sufficient.

What we propose as standard practice

Shipped as executable gates in the repo, not as advice. We recommend them for any self-improvement benchmark reporting a null.

  1. Known-good input, known-good output, asserted before every batch and run on the same allocation shape as the experiment — one defect lived entirely in the difference between a 1-GPU and a 3-GPU allocation.
  2. A dynamic-range precondition, reported as reachability: the fraction of tasks where the frozen base already clears the scoring anchor. Publish it beside every bank, and never interpret a contrast computed on a bank where it is near zero.
  3. A positive control on the causal path: an intervention known to move the metric. A null is interpretable only once the harness has registered a positive.
  4. Mechanism denominators beside every rate, so undefined is distinguishable from zero.
  5. Automated cross-artifact consistency checking — every number re-derived from the data files at build time.

None of these defects was unusual carelessness. Each was a single line, each was locally reasonable, and each was caught only because an assertion was looking for it. The generalizable claim is structural: in a benchmark whose headline is a difference between two arms of one pipeline, the cheapest result to produce accidentally is a null — and the field has no convention requiring authors to rule that out.

01 / The five tasks

What each task measures

All five tasks use GPU kernels and the same grader. A kernel is correct when its output matches the fp32 reference; speed is scored against an eager baseline (a unified torch.compile baseline is reported separately), headroom-normalized against a per-task roofline. Task 1 is a single solve. Task 2 improves the weights across rounds. Task 3 improves the executable procedure with weights fixed. Task 4 has a closed model rewrite an open trainee's harness. Task 5 — the true-RSI metric — has the model author its own strictly-harder tasks and improve on them, with a 3-arm design that isolates author co-evolution.

Task 1, Capability

Can the model write a correct and fast kernel in one shot. Correct means it matches the fp32 gold. Fast means it beats the eager baseline today, with a compiled baseline being added. Correctness ranks the low and mid band. Real speedups separate the frontier.

reports correct rate, fast rate, mean C

Task 2, RSI open weight

Does self improvement compound. Each round the model writes kernels for a train split, trains on its own correct kernels, and is re-scored on a held out split. The weights change, so the improver itself gets better. A frozen or API model cannot cross this line.

reports C per round, delta vs frozen base and control

Task 3, Procedure RSI open and closed

A closed model cannot change its weights, but it can improve its own executable research procedure. The editable state is a strategy library, a solver prompt, and an archive of verified kernels. Each round the model solves tasks, then rewrites its own procedure from the evidence. The improved procedure drives the next round. Weights stay fixed. This is how API models join the RSI axis.

reports Q per round, F = newer procedure beats older, vs frozen and archive-only controls

Task 4, Closed → Open closed drives open

A closed frontier model rewrites the training harness of an open-weight trainee — data selection, LoRA hyperparameters, curriculum. Improvement is transferred through tooling rather than the closed model's own weights. Scored as improved-harness vs frozen-harness on the same open trainee.

reports open-trainee C under improved vs frozen harness (headroom score)

Task 5, Self-play true RSI · open + closed

The model authors its own strictly-harder tasks and solves+improves on them, so difficulty and capability co-evolve. Three arms — STATIC, FROZEN-AUTHOR, LIVE-AUTHOR — isolate the one effect that matters: does an evolving author help beyond any harder curriculum? Anti-reward-hacking gates reject degenerate self-authored tasks.

primary L−F = author co-evolution; also L−S, F−S, model-authored acceptance rate

Task 2, does self improvement compound

Open models only, five rounds on the difficulty standardized hard bank. Three arms run in parallel. Self trains on its own kernels. Fresh-frozen trains on kernels freshly sampled from the unchanged base each round. Round0 retrains on the first round's data. The key column is self vs fresh-frozen. A positive value means an improving producer causes better descendants than a frozen producer given the same fresh data. That is the causal recursion signal, stronger than beating a static replay. Correctness and compiled speedup are shown separately so a gain in reliably writing a correct kernel is not confused with a gain in writing a faster one.

ModelFamilyroundsC0final correctcompiled xdelta vs frozenself vs fresh-frozenverdict
What the board shows, read honestly. Models with headroom that compound show a positive self vs fresh-frozen, so their improving producer beats a frozen one (DeepSeek-1.3B, Llama-3.1-8B). Models that only gain from fresh data show self vs fresh-frozen near zero, and the column separates the two. Per-scale banks remove the headroom confound. This first board used a single bank filtered against a frozen 7B, which saturated models of 7B and up (correct-rate near 1.0) and made them look flat. That is fixed. Each model now runs on a bank difficulty-filtered against a frozen anchor of ITS OWN scale (small 1.5B, mid 7B, large 14B), scored on speed vs torch.compile where every size has room. On that per-scale speed board, DeepSeek-1.3B reaches self vs fresh-frozen near +0.26. The score is a thermometer, not a cheerleader.

But read this column with the fork control. A positive self−fresh-frozen says the self-trained producer beats a frozen one; it does not establish compounding. The recursion-interruption control (clone the lineage, freeze the producer at a checkpoint, continue both at equal budget) dissolves it: for DeepSeek-1.3B, continued-self minus checkpoint-frozen is −0.001 — a one-time producer upgrade, not compounding. The decisive longitudinal test is lineage vs. matched reset, and that is TOST-equivalent to zero (see Key findings). Treat the rows below as a producer-quality snapshot, not evidence of recursion.

03c / Baselines, is it really recursion

Recursion vs just more sampling

Every gain is checked against non-recursive methods at the same generation budget (best-of-k sampling, in-context self-refine, archive retrieval), all frozen-weight and scored with the identical grader. recursion gain = weight-RSI final C minus the best non-recursive baseline. Positive means training on your own kernels beats simply sampling more.

Modelweight-RSI Cbest-of-kself-refineretrievalrecursion gain
Why this matters. A benchmark that only shows "the number went up" cannot tell training from extra sampling. At matched budget, Qwen-2.5-Coder-1.5B reaches 0.237 with weight-RSI versus 0.182 with best-of-20 sampling, a recursion gain near +0.055. Self-refine and retrieval arms fill in as they finish.

Task 3, a model improving its own procedure

A model with fixed weights rewrites its own executable research procedure each round (strategy library, solver prompt, verified-kernel archive). Q is held-out quality of the current procedure; the key column is Q gain vs the frozen procedure (self-modify arm). Open and closed models both compete.

ModelModeroundsQ0Q finalQ gain vs frozenverdict
Read this board as one-shot improvement, not compounding. The Q-gain vs a frozen procedure is real and sometimes large, but restricted to runs with ≥3 completed rounds, 76% of the total gain arrives at round 0 and 60% of runs are non-recursive — the archive saturates by round 1–2 (strategy-space exhaustion) while the self-written strategies stay diverse (Jaccard 0.12), so the bottleneck is converting strategies into capability, not strategy homogeneity. 03f / Task 5 — Self-play, the true-RSI metric

The aggressively-recursive task: the model authors the frontier that fights it

Fixed-task self-training only delivers a one-time upgrade (our recursion-interruption control shows continued-self ≈ checkpoint-frozen once the bank is fit). Task 5 removes that ceiling: the model itself authors strictly-harder tasks and solves+improves on them, so difficulty and capability co-evolve. To separate a harder curriculum from a co-evolving author we run three arms at equal budget on one fixed held-out ladder — S STATIC (fixed frontier), F FROZEN-AUTHOR (frontier escalates, author is the frozen base), L LIVE-AUTHOR (author is the current, evolving model). Only the author role differs between F and L.

Status: undefined, not null. In the runs below the live authors did not yield enough accepted valid tasks for L−F to be a measurement. We report the rung as an author-yield failure and place no L−F value in the headline claims. The design below is what the instrument was built to test; the data do not yet test it.
The decomposition. L−S = total adaptive-curriculum benefit · F−S = benefit without updating the author · L−F = benefit of author co-evolution, the self-referential signal and the primary metric. Sustained L−F > 0 with model-authored tasks accepted is genuine recursive compounding; L ≈ F means "adaptive curriculum only." Every authored task passes an anti-reward-hacking gate (no constant / identity / no-op / trivial-runtime tasks), is deduplicated, and its provenance is logged. Runs for open-weight (weight channel) and closed API (procedure channel) models.
Why this is the real RSI test. Compounding requires an open-ended frontier, an improving process, and novelty pressure — all exercised only when the challenge escalates and the escalation is driven by the improving model. The FROZEN-AUTHOR arm is what makes the claim airtight: it isolates co-evolution from "any harder curriculum."

Reading the self-play boards — start with the authored column. L−F is only defined if the LIVE author actually produced accepted, valid, novel tasks. We require ≥5; below that a row is greyed and marked undefined · author yield, because the co-evolution channel never engaged — that is not the same as engaging and returning zero. On the current data only 6/24 open and 5/11 closed runs clear the floor, and every closed row is exactly 0.0 (including authors that proposed 36–37 tasks across 24 rounds). The largest open L−F on this board (+0.232) rests on a single accepted authored task and is not a positive result.

What Task 5 currently shows is therefore a narrower but real finding: free-form task proposal collapses. Without constrained, executable task mutation — a DSL over verified seed tasks, with validity and learnability gates applied identically to the F and L arms — the author never manufactures a frontier, so co-evolution cannot be tested at all. That makes structured mutation a prerequisite experiment, not an extension.

03e / Mechanism

Why RSI fails, or how it passes

A rising curve says whether a model compounds; this probe says why. Every round we log generation diversity (mode collapse), predictive entropy, LoRA weight-drift by transformer depth (→0 = ceiling reached), retention on already-solved tasks (forgetting), and the train−held transfer gap (memorization). A verdict attributes each outcome to a mechanism — diversity_collapse, forgetting, drift_saturation, no_transfer, no_headroom — or PASS plus the depth that carries the learning. Each line is a model, across families and sizes 0.5B→32B.

The mechanistic finding — and one correction. Compounding is not about scale per se; among models that clear the correctness wall, the discriminators are sustained LoRA drift and retention (~5× higher in compounders). Diversity is not one of them. On this bank compounders show lower mean generation diversity than flat runs (0.41 vs 0.52), so "diversity collapse causes the null" is not supported — what compounding looks like here is productive convergence onto a good basin, not preserved exploration. Diversity contraction remains a plausible cross-round option-value lock, but that is an association whose clean test is a diversity-preserving intervention we have not run. All of these are associations, not established causal gates.

Why a family-disjoint bank. The 29-task bank behind the p-maps and the probe is too small for per-task statistics — probe AUC swings 0.71–1.00 across draws and a "+0.45 lift" is about five problems. The mutation-DSL bank crosses 16 op families × shape × dtype × variant and splits at the level of the computation: heldout_family families (grouped reductions, cumulative scans, top-k gating, rotary pairing, log-sum-exp, softmax→matmul) never appear in training, while heldin_cell holds out unseen dtype/shape cells of seen families. A renamed template or a nearby shape is not a new family, so the family count — not the task count — bounds any transfer claim.

Every task passes a CPU gate (builds, finite, non-constant, not an identity/no-op) before it can cost GPU time, and the gate itself must first pass a self-test on nine known-degenerate tasks — a gate that never rejects anything is indistinguishable from a broken gate. Status: generated and semantically valid, not yet difficulty-calibrated; the roofline ceiling and learnability filter still need a GPU pass, so this bank does not yet produce headline scores.

05 / Submit

Add your model — automated through GitHub

Open a pull request adding one JSON file under submissions/<track>/. A bot validates it, rebuilds the community board, and your row appears flagged self-reported; a maintainer then re-runs it on the private held-out split to mark it verified. Submitter code never runs on our GPUs from a PR — the held-out eval is a gated, maintainer-only job.

Do I submit a model, or something else? RSI is not a weight state you can upload — you cannot "fine-tune a model for RSI." RSI is a protocol we run on a base model. So the submission unit depends on the track:

Rows move through three honest states: self-reported (schema-valid submitter numbers) → ↻ reproduced (a maintainer re-ran it) → ✓ held-out verified (re-run on the private held-out split). Model and recipe rows are never merged into one ranking; external models, tools, and human input must be disclosed. For RSI/harness rows we meter training and search against a declared budget and run matched reset + search-only controls, so a gain can't be faked by spending more compute.
