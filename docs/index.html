Two tasks: Capability and RSI

KernelAscent asks two questions on the same substrate — GPU kernels. Task 1 — Capability: can a model write a kernel that is correct (matches fp32 gold) and fast (beats torch.compile)? Task 2 — RSI: when an open-weight model trains on its own correct kernels, do its weights keep getting better round after round — recursive self-improvement? Each task has its own dataset and a held-out split.

01 — THE TWO TASKS

What each task measures

Both run on GPU kernels and are graded the same way — a candidate kernel is correct if its output matches the fp32 reference and fast by its speedup over eager / torch.compile. They differ in what is being tested: a single solve (Capability) vs. improvement over rounds (RSI).

Task 1 — Capability

Can the model produce a correct, fast kernel in one shot? Graded on GPU: correct = matches fp32 gold; fast = speedup over min(eager, torch.compile). Two walls — correctness ranks the low/mid band, beating torch.compile is the frontier discriminator.

measures: correct-rate · fast-rate · mean C
score any model
evaluate --track capability \
  --api-model us.anthropic.claude-opus-5 --tier medium

Task 2 — RSI open-weight only

Does self-improvement compound? Each round the model writes kernels for a train split, is LoRA-retrained on its own correct kernels, and is re-scored on a disjoint held-out split. Because the weights change, the improver itself gets better — the ceiling a frozen/API agent cannot cross.

measures: C_r per round · Δ vs frozen-base & round-0-data controls
score an open-weight model (GPU)
lab_weight_rsi --model Qwen/Qwen2.5-Coder-7B \
  --rounds 6 --k 4
02 — DATASETS

One dataset per task, each with a held-out split

Every task ships a public split (committed + on HuggingFace) for development and a disjoint held-out split that is never released — the leaderboard is scored only on held-out, so scores can't be overfit. Full taxonomy: TIERS.md.

TaskDatasetTiersPublic splitHeld-out (scoring)
Capability GPU-kernel bank L1 memory/reduction · L2 matmul+epilogue · L3 attention/norm HF · dataset/kernel_bank/ disjoint kernel set, unreleased
RSI RSI kernel bank (Fable-5.1-curated, GPU-validated) L1 memory/reduction · L2 matmul+epilogue · L3 attention/norm dataset/kernel_bank/ (train split) held-out kernels re-scored every round

Both tasks draw from the same tier taxonomy so a kernel technique learned at one tier is testable at another. The RSI task splits its bank into a train set (the model writes+learns from these) and a held-out set (used only to measure C_r) — the two never overlap.

04 — SUBMIT

Add your model — either task

Everything is dockerized behind one entrypoint; the leaderboard is scored on a private held-out split, so results can't be overfit.

docker build -t ka -f docker/Dockerfile .

# Task 1 — Capability (any model)
docker run --rm -e AWS_SHARED_CREDENTIALS_FILE=/creds -e AWS_PROFILE=bedrock \
  -v $PWD/creds:/creds:ro -v $PWD/out:/out ka \
  --track capability --api-model <model> --tier medium

# Task 2 — RSI (open-weight, GPU)
docker run --rm --gpus all -v $PWD/out:/out ka \
  --track rsi --model <hf-id> --rounds 6 --k 4

# each writes out/scorecard.json

Open a model-submission issue with your scorecard.json (state the task). Maintainers re-run on the held-out split and add your row. Self-check with docker run --rm --entrypoint bash ka docker/entrypoint_selfcheck.sh.
