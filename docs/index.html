Recursive Self-Improvement Benchmark

Can a model improve the machinery that makes it better?

KernelAscent measures recursive self-improvement at the substrate level: a model optimizes the GPU kernels used to train itself. Under a fixed wall-clock budget, faster kernels buy more effective training, producing a stronger model that optimizes kernels better. The question is whether capability compounds across rounds, or plateaus.

Why this benchmark

Recursive self-improvement (RSI) is the central capability behind intelligence-explosion concerns, yet it has almost no rigorous quantitative benchmark. Two literatures never meet:

  • Kernel-generation benchmarks (KernelBench, TritonBench, RE-Bench, robust-kbench, Kevin-32B) measure a one-shot artifact: can a model write a fast GPU kernel? That capability is now established.
  • Self-improvement systems (STOP, ADAS, Darwin Gödel Machine, SICA) rewrite their own scaffold code, but never touch the compute substrate and never measure whether capability compounds.

KernelAscent closes the loop neither camp closes: the agent improves the machinery that produces its own capability, and we measure the compounding coefficient — the slope of capability over self-improvement rounds. GPU-kernel optimization and training throughput are exactly the levers a self-improving AI-R&D system would pull to accelerate its own development.

The kernel → model loop

The benchmark is grounded in genuine capability self-improvement, not a rhetorical loop. Each round:

  1. Optimize. Model Mk writes optimized GPU kernels for its own training stack (attention, GEMM, normalization, fusions).
  2. Train. Under a fixed wall-clock budget, those faster kernels are the only way to buy more gradient steps → a stronger model Mk+1.
  3. Re-measure. Mk+1 is re-scored on held-out kernel-optimization tasks.

The headline result is the RSI signal Δk = Ckself − Ckcontrol against a matched control that trains with round-0 kernels. RSI is confirmed only if Δk grows with k; a null result — capability rising only from more compute, not self-improvement — is reported honestly as a negative finding.

Tasks & difficulty

Every task is a self-contained PyTorch Model whose forward is a fused op-graph; an agent must return an optimized, numerically-equivalent ModelNew.

Families (6)

matmul (GEMM + fused epilogue) · norm-act (softmax / LayerNorm / RMSNorm / GELU chains) · attention (causal / non-causal) · RoPE-attention · quantized int8 dequant-GEMM · soft-MoE (gated experts / grouped GEMM).

Tiers

L1 memory/reduction · L2 tensor-core / matmul-epilogue · L3 attention & arch-specific. Difficulty is calibrated by a strong curator model.

Difficulty labels

accessible medium hard frontier — derived from whether the strong curator beats the roofline, and by how much.

Scoring

Correctness vs fp32 gold

A candidate passes only if its relative L2 error to an fp32 gold is no worse than the reference's own fp16/bf16 rounding error. We never demand more precision than the dtype allows.

Roofline-relative speedup

speedup = tbaseline / tcandidate, where the baseline is the strongest automated reference (min of eager and torch.compile). Beating it is the challenge.

fast_p, pass@k

fast_p = fraction of tasks beating p× speedup. Geomean over passing tasks only. Timing is warmup + median-of-N + L2 flush on clock-pinned GPUs.

Reproducible & held-out by construction

Every scored task is synthesized from a seed at generation time — a randomized fused-op-graph (or attention / RoPE / quantized / MoE pattern) over varied shapes and dtypes. Generation is fully deterministic, so results are reproducible for papers, while task instances are freshly composed rather than drawn from a fixed public list. A private held-out seed range powers the leaderboard; the public dev split uses a disjoint range. Frontier models may also propose novel problems, which pass a firewall (gradeable · non-trivial · structurally deduped) and are kept out of the held-out set.

Generation (frontier model, network-bound) is decoupled from grading (GPU-bound), so credentials stay off the compute box and grading shards across GPUs. Each graded task becomes a complete bundle: task.py, candidate solutions, a reference_solution.py (best correct + fastest kernel), results.json, and difficulty metadata. The RSI loop layer adds a task→training-op registry, a fixed-wall-clock training harness, and per-round records that yield the compounding coefficient.

Dataset & splits

KernelAscent ships a two-split design, standard for a leaderboard you can trust.

Public dev set

242 tasks (57 L1 · 109 L2 · 76 L3) across all 6 families in dataset/public/ — problem definitions + metadata. Use it to benchmark your own models and in research papers. Regenerate deterministically: python kernelascent/make_dataset.py --split public --outdir dataset/public.

Private held-out

A separate, undisclosed seed range powers the leaderboard. It is never committed, so public numbers can't be gamed by overfitting the released tasks. Maintainers run it on submissions.

Deterministic & fresh

Every task is synthesized from a seed — fully reproducible for papers, and composed at generation time rather than drawn from a fixed list. Public and held-out seed ranges never overlap.

Submit a model

The leaderboard is data-driven. To add an off-the-shelf model:

  1. Run the agent harness on the public task split: python kernelascent/agent_bench.py --n 80 --k 8 --out results.json (or grade your own candidates with grade_candidates.py).
  2. Add one entry to docs/data/leaderboard.json with your model, params, and metrics.
  3. Open a pull request. Held-out (private) scoring is run by the maintainers to confirm.

See the GitHub repository for the harness, generator, and proposal.
