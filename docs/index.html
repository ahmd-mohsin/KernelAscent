Agents that improve with experience

Does self-improvement compound?

Not "can an agent solve a task?" — but: when an agent improves the research procedure it uses, does using that improvement causally produce a better next improvement, and does it repeat? KernelAscent measures this with two evaluation settings, actor/target-separated causal estimators, and calibrated instruments.

01 — MECHANISM

How we measure RSI

An agent's state U is its executed research procedure. develop(U) runs it on a fresh task under a fixed budget and returns a quality Q. revise(actor, target) lets an actor edit a copy of a target procedure to produce a child. The trick: in a causal fork, two different actors edit the identical target — so a later actor earns credit only if it builds a genuinely better child.

02 — TWO SETTINGS

What you can evaluate

Every submission reports the axes separately. Both settings share the same estimators; they differ in the substrate.

Capability setting A

Can the agent produce a correct, fast solution? Two banks: GPU kernels (correctness vs fp32-gold, speedup vs min(eager, torch.compile)) and a code bug-fix bank (produce a correct patch; a local verifier selects it).

measures: Q₀ · correct-rate · fast-rate · verifier_dQ

Two walls — correctness ranks the low/mid band; beating torch.compile is the frontier discriminator.

score a model
evaluate --track capability \
  --api-model us.anthropic.claude-opus-5 \
  --tier medium

Recursion setting B — RSI

Does improving the procedure compound? The improvable state is a growing archive of reusable, debugged abstractions (a build-test-fix library). Two tiers by how load-bearing the archive is:

  • R1 · shared-helper — tasks share number-theory/digit primitives; exposes first-order improvement (and the negative regime).
  • R2 · compositional tower — a depth-D ladder where rung k = layer ∘ rung k−1; from-scratch correctness compounds down, so a verified archived rung is required — the setting where F₂ compounding is measurable.
measures: q₁−q₀ · N · F₁ (causal link) · F₂ (compounding)
score a model
evaluate --track rsi \
  --api-model us.anthropic.claude-opus-5 \
  --lineages 12

04 — FINDINGS

What the benchmark shows

Agents do improve with experience. On the load-bearing open-ended substrate, first-order self-improvement is resolved and capability-graded — the strongest model measurably improves its own research procedure (Opus-5 q₁−q₀ = +0.083, CI clears 0), and its produced child beats the unchanged target (N₁ resolved > 0).

And the instrument resolves compounding when it's there. On a scripted open-ended substrate, F₁ and F₂ are resolved above zero and accelerating (F₂ > F₁), while a frozen-archive-plus-memory control is exactly 0 — proving the estimator detects genuine recursion and isn't fooled by mere memory. This is what makes it a real thermometer.

Is it fully recursive (compounding) for a live model? Not yet — and that is the point. No current model shows resolved live compounding (F₁/F₂ still span 0); that is the open frontier this benchmark exists to detect, and it will read positive the moment a system genuinely compounds. A benchmark that always answered "yes" would measure nothing.

The result that survives: archive-based self-improvement helps the strongest model (Opus q₁−q₀ resolved > 0) and hurts weaker ones (Gemma, Llama resolved < 0) — weak models poison their library with buggy abstractions. Compounding is measurable; eliciting it live needs a harder-to-re-derive substrate (GPU kernels).

06 — SUBMIT

Add your model — both settings

Everything is dockerized behind one entrypoint; the leaderboard is scored on a private held-out split, so results can't be overfit.

docker build -t ka -f docker/Dockerfile .

# Setting A — Capability
docker run --rm -e AWS_SHARED_CREDENTIALS_FILE=/creds -e AWS_PROFILE=bedrock \
  -v $PWD/creds:/creds:ro -v $PWD/out:/out ka \
  --track capability --api-model <model> --tier medium

# Setting B — Recursion (RSI)
docker run --rm ... ka --track rsi --api-model <model> --lineages 12

# each writes out/scorecard.json

Open a model-submission issue with your scorecard.json (state the setting). Maintainers re-run on the held-out split and add your row. Open-weight models run on GPU with --model <hf-id> --gpus all; self-check with docker run --rm --entrypoint bash ka docker/entrypoint_selfcheck.sh.
